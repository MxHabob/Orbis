# Local Performance Diagnostics

Orbis API performance logs are generated by the API server process and stay in
the institution's configured server logging environment. No monitoring service
or external telemetry destination is required.

## API request timings

Requests that take at least 500 ms are logged at warning level by default.
Server errors are also logged, even when they complete faster. Each event
includes the HTTP method, matched route template, response status, and elapsed
milliseconds. Request bodies, query strings, organization IDs, and concrete
record IDs are not included.

Set `ORBIS_SLOW_REQUEST_MS` to change the slow-request threshold. Values must be
positive integer milliseconds:

```powershell
$env:ORBIS_SLOW_REQUEST_MS = "750"
```

```sh
export ORBIS_SLOW_REQUEST_MS=750
```

To include timings for requests below the warning threshold, enable the
performance target at debug level:

```powershell
$env:RUST_LOG = "info,orbis::performance=debug"
```

```sh
export RUST_LOG="info,orbis::performance=debug"
```

Review the server's standard output or its institution-managed log destination.
Start by grouping slow events by `route`; compare repeat occurrences and status
codes before changing indexes, caching, or connection-pool settings.

## Desktop command timings

In the desktop app, open **Settings → Database Management → Performance
Diagnostics**. The panel measures Tauri IPC round-trip time for desktop commands
and shows totals, recent average and P95, and failures for the current app
session. It is an in-memory diagnostic view; it does not persist or export
measurements.

The desktop collector keeps at most the latest 100 durations per command and
performs no file, database, or network writes. It records only the command name
and timing metadata, never command arguments or returned data. Open or refresh
the panel to calculate and display the snapshot; it does not poll in the
background.

For the API connection mode, request timings are measured by the API server and
remain in that server's local logs. The desktop panel does not claim to measure
server-side handler or SQL time.

## PostgreSQL query analysis

The API request timing identifies slow operations, but does not yet attribute
time to individual SQL statements. For PostgreSQL deployments, administrators
can optionally enable the local `pg_stat_statements` extension to inspect
aggregated query timings. This is a PostgreSQL server setting and is not enabled
or modified automatically by Orbis; it may require a database restart and
administrator privileges.

After enabling the extension for the Orbis database, an administrator can review
the most expensive normalized statements with:

```sql
SELECT
    calls,
    round(total_exec_time::numeric, 1) AS total_ms,
    round(mean_exec_time::numeric, 1) AS mean_ms,
    rows,
    left(query, 160) AS normalized_query
FROM pg_stat_statements
ORDER BY total_exec_time DESC
LIMIT 20;
```

`pg_stat_statements` reports aggregate statistics locally; it does not transmit
institution data. Apply database changes only after reviewing the statements
and validating the change against the institution's workload.
