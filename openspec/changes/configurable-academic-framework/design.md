# Design

## Context

راجع `proposal.md` والمواصفات المرتبطة به. حاليًا يوجد فصل جزئي بين `academic_years` و`academic_periods` و`assessment_schemes` و`grades`، لكن التقييم العملي يجمع فترات شهرية ثم نتيجة فصلية/سنوية ثابتة في `AcademicCalculationEngine`. مخطط التقييم يخزن المكونات في `components_json`، بينما `AssessmentScheme` يضع افتراضيًا نوعًا شهريًا، وواجهات النتائج تعرض ملخص الفصل والسنة. يعتمد `class_subjects` على فترة وصف/مقرر واحد، ولا يمثل كتالوج مقرر وعرضًا وتسجيل محاولة تعلم مستقلة. يقبل DocForge سياق JSON عام، ولا يفرض عقدًا أكاديميًا typed.

يلزم الحفاظ على SQLite وPostgreSQL، ومعرّفات وبيانات المؤسسات القائمة، وعقود API الحالية خلال الانتقال. يجب أن يبقى حساب النتيجة مستقلًا عن قاعدة البيانات وواجهة التقارير.

## Goals / Non-Goals

**Goals:**

- جعل التقويم، هيكل الفترات، عروض المقررات والتسجيلات، التقييمات، قواعد الحساب، النتائج والتقارير حدودًا مستقلة مترابطة بمعرّفات واضحة.
- بناء محرك حتمي قابل للاختبار من أنواع وقواعد محددة، لا فروع حساب خاصة بنوع المؤسسة.
- حفظ إصدار القاعدة والمدخلات والنتيجة المعتمدة بما يسمح بإعادة عرض التاريخ وتتبّع التصحيح.
- توفير إعدادات بداية مؤسسية اختيارية قابلة للتخصيص دون إنشاء سجلّات تشغيلية تجريبية.
- الحفاظ على عقود typed قابلة لإعادة الاستخدام مع API وSDK وDocForge.

**Non-Goals:**

- فرض توحيد دولي لمصطلحات الفترات أو مقاييس الدرجات أو حالات النجاح.
- استبدال نظام القوالب والمستندات أو فرض شكل شهادة أو تقرير موحد.
- تقديم محرر مرئي عام للمعادلات في المرحلة الأولى؛ تكوين القواعد يتم عبر عقود API وإعدادات مُتحقق منها.
- إضافة محرك حساب ثانٍ موازٍ للمحرك الحالي؛ يُستبدل مسار الحساب الثابت تدريجيًا بمحرك واحد ذي توافق انتقالي.

## Decisions

### 1. فصل الهوية الأكاديمية عن نوع المؤسسة

تكون المؤسسة مالكة لـ`academic_calendar` اختياري، وتكون الفترات عقدًا هرميًا ذا أنواع مؤسسية معرفة في `academic_period_types`. تحفظ النماذج الجديدة في `academic_calendars` و`academic_calendar_periods` كي لا يُجبر التقويم العام على `year_id` الإلزامي في المخطط القديم. لا تحمل الفترة معنى «شهر» أو «ترم» للحساب بذاتها. تبقى `academic_years` و`academic_periods` حدود توافق للبيانات والمسارات القديمة أثناء الانتقال، ولا تكون مصدر كتابة للواجهات الجديدة. تُعرّف الكيانات منفصلة لكتالوج المقرر، وعرض المقرر، وتسجيل المتعلم/محاولته، ومشاركة البرنامج أو الدورة عند الحاجة. يمكن أن يشير العرض أو التقييم إلى فترة، لكن لا تُفرض تلك العلاقة عندما لا تنطبق.

تستخدم هوية العرض/التسجيل الجديدة حدود مؤسسة مركبة وعلاقات مرجعية قابلة للتحقق. لا نعيد تفسير `class_subjects` أو `enrollments` القديمة ضمنيًا: يُضاف جسر توافق موثق يحول السجلات المؤكدة إلى السياق الجديد، وتظل العلاقات الأصلية متاحة أثناء الترحيل.

**البدائل المرفوضة:** جعل `period_type` قائمة أسماء جديدة فقط؛ أو توسيع JSON في `academic_periods` ليحمل كل مفاهيم المقرر والتسجيل والتقييم. كلاهما يبقي الاقتران ويضعف التحقق المرجعي.

### 2. نموذج قواعد typed محدود بدل JSON غير محدد

تُحفظ المقاييس، حدود التقدير، حالات النجاح، الأوزان، وحدات الاعتماد، قواعد الترتيب، مدخلات ومخرجات التجميع ككيانات/حقول typed وعلاقات قابلة للتحقق. تمثل المعادلة AST محدودًا من أنواع operands/operators مع إصدار مخطط، ومراجع مسماة typed، وحد أقصى للعمق والعقد. لا يُسمح بكود أو دوال تنفيذية يرسلها العميل. يمكن ترميز AST كوثيقة JSON ذات union tagged ومخطط ثابت، لا كحاوية إعدادات عامة؛ بقية العلاقات تبقى علائقية.

ينفذ المحرك الحسابات الرقمية على Decimal، ويفشل صراحةً عند مرجع أو مقياس غير متوافق أو قسمة على صفر. تطبق التحويلات والتقريب في ترتيب معلن بالسياسة. يحول التقديرات الكمية/الفئوية ومخرجات النجاح عبر قواعد مستقلة. المعدل الموزون والترتيب تجميعان اختياريان بمدخلات واستبعادات وتعادل معرفة، وليس حقولًا إلزامية في نتيجة كل مؤسسة.

**البدائل المرفوضة:** الإبقاء على توابع `calculate_monthly` و`calculate_annual` ثم إضافة فرع لكل مؤسسة؛ أو تخزين السياسة كلها كـJSON غير typed. الأول يضاعف المحركات، والثاني يمنع سلامة الأنواع والترحيل والاستعلامات.

### 3. إصدارات غير قابلة للتغيير ولقطات نتائج

تعديل قاعدة حساب ينشئ `policy_version` جديدًا، ولا يحرر الإصدار المستخدم في نتائج محسوبة أو معتمدة. تحفظ لقطة النتيجة مراجع إصدار الخطة والمدخلات ومراجعاتها، مخرجاتها typed، حالة الاعتماد، وتجزئة محتوى المدخلات اللازمة لاكتشاف التغير. تحفظ تغييرات الدرجة كتعديلات مدققة؛ والاعتماد/النشر انتقالات حالة محمية بصلاحيات ومعاملة متسقة. تصحيح نتيجة معتمدة ينشئ لقطة لاحقة مرتبطة بالأصل مع السبب والمنفذ، ولا يمحو الأصل.

**البدائل المرفوضة:** إعادة الحساب عند كل طلب تقرير، أو تحديث نتيجة معتمدة عند تغيير مخططها؛ كلاهما يغيّر التاريخ بأثر رجعي ويجعل التقرير غير قابل لإعادة الإنتاج.

### 4. إعدادات البداية بيانات مرجعية وليست محركًا حسب المؤسسة

تقدم Bootstrap وOnboarding ملفات إعداد أكاديمي typed مُسماة وقابلة للتخصيص. يختار نوع المؤسسة مجموعة اقتراحات فقط: مثل مقياس درجات مدرسي اختياري، أو سياسة ساعات ومعدل، أو وحدات وتقييم كفاءات. لا تترجم هوية المدرسة آليًا إلى شروط إلزامية في المحرك أو Onboarding، ولا تنشئ الإعدادات مقررات أو فصولًا أو متعلمين تجريبيين. يمكن للمؤسسة تخطي التقويم والفترات الشهرية أو تحريرها قبل التفعيل.

تكون الملفات التعريفية بيانات إعداد قابلة للتحقق؛ ويحدد Registry typed الملف المختار بدل تكرار `if/else` في الحساب أو التقييم. تبقى نسخة الإعداد التي اعتمدتها المؤسسة محلية لها.

**البدائل المرفوضة:** تقويم ومدرسة افتراضيان يزرعان سجلات التشغيل عند بدء النظام؛ أو تفرعات per-institution داخل حساب النتائج.

### 5. التوافق عبر API وDocForge بعقد دلالي

تُعرض العمليات الجديدة عبر DTOs وOpenAPI typed ويولد SDK منها. تبقى مسارات الفصل/السنة الحالية محولات توافق على عقود النتائج الجديدة خلال نقل عملاء Desktop وMobile، ثم يمكن إيقافها في إصدار معلن بعد التحقق من الاستخدام. لا يستخدم العميل جدول `grades` لاشتقاق النتيجة.

تقدم خدمة النتائج عقدًا دلاليًا versioned مثل `AcademicResultView` يصف هوية المتعلم والتسجيل والسياق ومجموعة مخرجات مسماة typed ومصدر اعتمادها. يقدم هذا العقد بيانات DocForge ومخطط الحقول وتسميات التحرير. يستقبل القالب عقد العرض لا جداول التخزين؛ وتثبت مهمة التقرير revision واحدة قبل بدء الطباعة. لا يفترض العقد «شهادة»، ولا يفرض `AnnualSummary` أو `TermSummary`.

**البدائل المرفوضة:** تمرير `serde_json::Value` حر من جداول قاعدة البيانات إلى كل قالب؛ أو جعل محرك DocForge يفسر قواعد الدرجة. كلاهما يربط القالب بالتخزين أو الحساب.

### 6. قاعدة البيانات والاستعلامات

تضاف جداول ذات نطاق `org_id`، ومفاتيح فريدة مركبة، ومفاتيح خارجية وفهارس على نطاق المؤسسة والعرض/التسجيل والفترة وحالة النتيجة. تستخدم أعمدة Decimal أو تمثيلًا عشريًا مكافئًا متوافقًا عبر SeaORM وSQLite وPostgreSQL؛ ولا تستخدم floating point لحساب الدرجات. تظل البيانات العرضية أو UI-only خارج مخطط النتائج.

تنفذ التقارير والحسابات المجمعة باستعلامات دفعية بحسب العرض/الفترة/التسجيل مع حدود pagination، ثم يحسب المحرك pure Rust دون استعلام لكل درجة. تحفظ اللقطات المعتمدة لتجنب إعادة حساب تقارير الدفعات، وتستخدم قيود فريدة/تزامنًا تفاؤليًا لمنع تكرار الاعتماد أو استبدال المراجعات.

## Risks / Trade-offs

- [بيانات قديمة تعتمد أسماء أنواع/شهور أو تلائم افتراض فصلين] → تُرحّل كما هي مع معرفات توافق؛ لا تُحوّل إلى نتائج معتمدة جديدة دون تقرير تدقيق ومراجعة مالك المؤسسة.
- [تغيّر API يكسر عميلًا قديمًا أو قالبًا محفوظًا] → تبقى المسارات والحقول القديمة محولات، وتضاف تحذيرات تحقق وتغطية SDK قبل الإزالة.
- [AST قابل للتكوين قد يصبح مكلفًا أو غير محدود] → allowlist لمشغلات typed، وحدود عمق/عدد عقد/دقة، وتحليل مسبق، ووقت/حجم تنفيذ مضبوط.
- [تعديل متزامن لدرجة واعتماد نتيجة] → تجميع المدخلات واعتماد اللقطة داخل معاملة، مع مراجعات/تزامن تفاؤلي وإعادة المحاولة بخطأ واضح.
- [SQLite وPostgreSQL يختلفان في دعم القيود أو أنواع JSON/Decimal] → استخدم أنواع ومفاتيح SeaORM المشتركة، واختبر ترحيلًا وتشغيلًا فعليًا على كلا المحركين.
- [ملفات الإعداد الافتراضية قد تتحول عمليًا إلى قواعد مفروضة] → اجعل إنشاء التقويم والمقاييس منفصلًا عن إنشاء بيانات التشغيل، واختبر أن إكمال Onboarding لا يشترط شهرًا أو مخرجًا بعينه.

## Migration Plan

1. إضافة مخطط typed للإصدارات والسياسات والتقاويم والعروض والتسجيلات والنتائج، مع اختبارات migrations على SQLite وPostgreSQL وعدم حذف أو تعديل أعمدة تاريخية.
2. إضافة سجلات إعداد افتراضية مؤسسية قابلة للتخصيص وتعديل Bootstrap/Onboarding لتقديم مقترحات لا بيانات تشغيلية ولا متطلبات شهرية عامة.
3. بناء محرك الحساب typed واحد واختباره منفردًا، ثم ربط إدخال التقييمات والعلامات تدريجيًا بالعروض والتسجيلات الجديدة مع مسارات توافق للبيانات القديمة.
4. تفعيل تخزين اللقطات والاعتماد والتصحيح، ثم عرض النتائج الجديدة عبر API وSDK وعقد DocForge typed؛ نقل Desktop وMobile وتقارير الدفعات إلى العقد.
5. تشغيل اختبارات قبول نماذج K-12 شهري وK-12 بلا أشهر، جامعة بساعات ومعدل، ومعهد بوحدات وتقييم عملي/كفاءات؛ بعد نجاحها تفعيل المسارات الجديدة افتراضيًا.
6. إزالة الاعتماد على الملخصات الثابتة فقط بعد رصد ترحيل البيانات وعملاء API. التراجع يكون بتعطيل الكتابة للمسار الجديد وإرجاع التوجيه إلى المحولات، دون حذف إصدارات أو لقطات.
